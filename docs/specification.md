# CodeRCA MVP Specification

| 属性 | 内容 |
|---|---|
| 状态 | Ready for implementation |
| 日期 | 2026-08-05 |
| 目标完成日期 | 2026-08-20 |
| 适用范围 | Python/Django 单仓库 CI 测试失败根因诊断 |
| 主要测试缝 | 诊断应用服务：Diagnosis Task → Root Cause Report + Events + Artifacts |

## Problem Statement

后端工程师面对 CI 测试失败时，需要在日志、故障变更、代码结构和测试行为之间反复切换，才能从失败表象定位真正的 Root Cause。现有的单次 LLM 问答通常只能根据日志和 diff 猜测原因：它不会持续维护可证伪的 Hypothesis，不会主动选择 Experiment 收集 Supporting Evidence 或 Contradicting Evidence，也无法证明修复建议恢复了正确行为。

对项目作者而言，单个精心准备的成功 Demo 同样不能证明其具备 AI Agent 工程能力。项目必须通过显式工作流、结构化工具协议、代码检索消融、沙箱 Validation、冻结数据集和公平 Baseline 对比，提供可复现、可审计、可量化的招聘证据。

## Solution

CodeRCA 提供一个面向本地单用户的 CI 根因诊断服务。用户提交包含仓库版本、CI 日志、故障变更、受控测试入口和执行预算的 Diagnosis Task。系统准备故障版本工作区，由单个诊断 Agent 运行显式的“Hypothesis → Evidence → Experiment”循环，自主选择代码检索、符号分析、diff 检查、测试、补丁和静态检查工具。

系统最多维护三个活跃 Root Cause Candidate。每次工具调用必须关联一个 Hypothesis、调用目的和预期 Observation。模型负责提出假设、选择实验和生成候选补丁；程序负责 Schema、权限、状态转移、预算、超时、事件和停止条件。Agent 只能访问 Public Validation；补丁封存后，独立评测器才执行 Hidden Validation。

最终产物是一个可追溯的 Root Cause Report，包含 Top-1/Top-3 候选、缺陷位置、因果机制、Supporting Evidence、Contradicting Evidence、Experiment 结果、修复建议、补丁验证状态、未知项、停止原因和运行成本。项目另提供检索消融、Raw Model Baseline、Fixed Pipeline 和动态 Agent 的冻结评测报告。

## User Stories

### 后端工程师

1. 作为后端工程师，我希望提交一个包含故障仓库版本和 CI 日志的 Diagnosis Task，从而启动一次可复现的根因诊断。
2. 作为后端工程师，我希望通过已注册的测试命令标识任务，而不是提供任意 Shell，从而避免诊断系统执行超出范围的命令。
3. 作为后端工程师，我希望系统在诊断开始前校验 commit、日志、镜像和测试入口，从而及早发现 Invalid Task。
4. 作为后端工程师，我希望看到当前 Diagnosis Run 的状态，从而知道任务正在准备、推理、实验、验证还是生成报告。
5. 作为后端工程师，我希望看到 Agent 当前维护的 Root Cause Candidate，从而理解系统正在调查哪些方向。
6. 作为后端工程师，我希望每个 Hypothesis 都关联 Supporting Evidence 与 Contradicting Evidence，从而区分有证据的判断和模型猜测。
7. 作为后端工程师，我希望每个 Experiment 都说明目的和预期 Observation，从而判断工具调用是否必要。
8. 作为后端工程师，我希望代码证据引用文件、Root Symbol 和行区间，从而快速核查结论。
9. 作为后端工程师，我希望日志和测试证据引用原始 artifact，从而避免摘要丢失关键错误信息。
10. 作为后端工程师，我希望 Agent 能根据中间 Evidence 改变后续诊断路径，从而处理固定流水线无法覆盖的故障。
11. 作为后端工程师，我希望 Agent 在沙箱中临时修改代码并运行 Public Validation，从而用实验验证 Root Cause。
12. 作为后端工程师，我希望实验改动与最终候选补丁分离，从而区分诊断插桩和正式修复建议。
13. 作为后端工程师，我希望系统按 Evidence Score 输出 Top-1/Top-3，从而优先查看最有证据的候选。
14. 作为后端工程师，我希望 Evidence Score 明确不是统计概率，从而不会误解模型置信度。
15. 作为后端工程师，我希望最终报告解释触发条件、缺陷位置、故障机制、传播路径和失败表现，从而理解完整因果链。
16. 作为后端工程师，我希望报告同时列出反证、失败实验和未知项，从而不会得到虚假的确定结论。
17. 作为后端工程师，我希望证据不足时系统明确停止并说明原因，从而避免强行编造 Top-1。
18. 作为后端工程师，我希望候选补丁附带 Public Validation 结果，从而知道建议是否至少恢复了可见行为。
19. 作为后端工程师，我希望真实仓库和生产环境保持只读，从而确保 Agent 只在临时工作区修改代码。
20. 作为后端工程师，我希望通过 CLI 运行和查看诊断，从而在不依赖 Web UI 的情况下完成主要工作流。
21. 作为后端工程师，我希望通过本地 API 提交任务、查询状态和读取报告，从而可以把 CodeRCA 集成进本地工具。
22. 作为后端工程师，我希望复杂运行能够回放真实事件轨迹，从而在模型服务不可用时仍可检查诊断过程。

### 技术评审者与面试官

23. 作为技术评审者，我希望看到结构化的 Hypothesis、Evidence 和 Experiment 事件，从而验证 CodeRCA 不是单次模型调用。
24. 作为技术评审者，我希望不同故障产生不同工具路径，从而验证工具选择不是硬编码顺序。
25. 作为技术评审者，我希望每次工具调用都有结构化原因和预期结果，从而判断 Agent 决策是否合理。
26. 作为技术评审者，我希望将动态 Agent 与 Raw Model Baseline 对比，从而观察工具与代码上下文带来的总体增益。
27. 作为技术评审者，我希望将动态 Agent 与公平的 Fixed Pipeline 对比，从而隔离动态决策本身的价值。
28. 作为技术评审者，我希望看到 BM25、向量、混合和 reranker 的检索消融，从而判断 RAG 组件是否有可测增益。
29. 作为技术评审者，我希望看到逐任务结果和失败案例，而不仅是汇总百分比，从而评估结论可信度。
30. 作为技术评审者，我希望看到 Token、模型调用、工具调用和耗时，从而评价质量与成本的权衡。
31. 作为技术评审者，我希望运行清单记录模型、prompt、索引、镜像和随机参数，从而复现实验结果。
32. 作为技术评审者，我希望项目声明有限的能力和安全边界，从而区分已证明能力与未来愿景。

### 数据集维护者

33. 作为数据集维护者，我希望每个任务绑定唯一的 Faulty Commit 和固定容器镜像，从而复现目标 CI 失败。
34. 作为数据集维护者，我希望每个任务标注 Root Symbol，从而确定性计算位置命中指标。
35. 作为数据集维护者，我希望每个任务标注触发条件、故障机制、传播路径、失败表现和正确修复行为，从而评估完整因果解释。
36. 作为数据集维护者，我希望每个任务包含参考补丁和 Hidden Validation，从而独立评价补丁正确性。
37. 作为数据集维护者，我希望任务在开发、验证和隐藏集合之间冻结划分，从而避免评测泄漏。
38. 作为数据集维护者，我希望修复 diff、答案性 commit message 和未来代码不进入 Agent 输入，从而避免答案泄漏。
39. 作为数据集维护者，我希望至少一半任务包含多个合理候选变更，从而避免诊断退化为查看单行 diff。
40. 作为数据集维护者，我希望三类支持故障在数据集中保持平衡，从而避免指标被单一故障类型主导。
41. 作为数据集维护者，我希望注入任务与真实修复任务分别标识，从而分别解释可控有效性和外部有效性。
42. 作为数据集维护者，我希望环境无法复现的任务标记为 Invalid Task，从而不把数据问题误计为 Agent 失败。

### 评测执行者

43. 作为评测执行者，我希望检索消融使用相同冻结查询，从而只比较检索配置差异。
44. 作为评测执行者，我希望核心 Recall@K 与 MRR 只按 Root Symbol 计算，从而不以模糊相关代码冒充根因命中。
45. 作为评测执行者，我希望上下游相关代码单独计算辅助覆盖率，从而观察检索到因果上下文的能力。
46. 作为评测执行者，我希望端到端评测只使用验证集选出的单一检索配置，从而避免组合爆炸与隐藏集调参。
47. 作为评测执行者，我希望三种诊断方案使用相同模型、输入、检索配置和验证环境，从而保证 Baseline 公平。
48. 作为评测执行者，我希望 Fixed Pipeline 的步骤和上下文上限在隐藏评测前冻结，从而避免事后调弱基线。
49. 作为评测执行者，我希望 Hidden Validation 在补丁封存后运行且结果不反馈给 Agent，从而保持隐藏评测有效。
50. 作为评测执行者，我希望缺陷位置和因果解释分别评分，从而避免测试通过掩盖错误解释。
51. 作为评测执行者，我希望 LLM Judge 按字段使用固定的 0、1、2 评分规则，从而减少整体印象分偏差。
52. 作为评测执行者，我希望 Judge 看不到系统名称和检索配置，从而降低来源偏见。
53. 作为评测执行者，我希望人工复核全部隐藏任务的因果评分，从而量化人与 Judge 的一致性。
54. 作为评测执行者，我希望最终 Agent 在隐藏任务上重复三次，从而评价 Top-1 稳定性。
55. 作为评测执行者，我希望任务无效、基础设施失败、模型失败、Agent 决策失败和诊断错误分别统计，从而正确解释失败来源。
56. 作为评测执行者，我希望只对确定无副作用的瞬时基础设施错误重试一次，从而避免重试改变实验语义。

### 项目开发者与本地操作者

57. 作为项目开发者，我希望 Agent 工作流由自研类型化状态机控制，从而能够解释和测试每个状态转移。
58. 作为项目开发者，我希望模型通过最小 ModelProvider 接口接入，从而替换本地或云端模型而不改变领域工作流。
59. 作为项目开发者，我希望模型结构输出失败后只允许一次纠错，从而显式暴露模型兼容性问题。
60. 作为项目开发者，我希望工具通过统一 Tool Spec 注册，从而集中管理 Schema、权限、超时和错误。
61. 作为项目开发者，我希望工具大结果保存为 artifact 并返回引用，从而避免上下文被日志和代码淹没。
62. 作为项目开发者，我希望代码按 AST 语义边界建立索引，从而保留函数、方法和类的结构信息。
63. 作为项目开发者，我希望检索后端对 Agent 保持统一接口，从而在不改变工作流的情况下执行消融。
64. 作为项目开发者，我希望 Python 符号关系明确标记为启发式近似，从而不对动态语言作出错误保证。
65. 作为项目开发者，我希望模型、工具和沙箱都能用替身或录制响应测试，从而让默认 CI 快速且稳定。
66. 作为本地操作者，我希望单个 worker 串行执行 Diagnosis Run，从而避免 8 GB GPU 和容器资源竞争。
67. 作为本地操作者，我希望服务重启后未完成运行标记为 interrupted，从而不会把残留状态当成成功任务。
68. 作为本地操作者，我希望容器默认禁网、非 root、限资源且不挂载凭证，从而限制测试代码对宿主的影响。
69. 作为本地操作者，我希望模型调用发生在测试容器之外，从而不向仓库代码暴露模型凭证。
70. 作为项目开发者，我希望事件以追加方式持久化，从而支持审计、回放和失败诊断。
71. 作为项目开发者，我希望大对象按内容哈希存储，从而去重并校验 artifact 完整性。
72. 作为项目开发者，我希望本地模型在进入完整评测前通过结构输出、工具调用、Top-3 和补丁门槛，从而避免在低质量后端上浪费评测成本。

## Implementation Decisions

1. **产品边界**：MVP 只支持 Python/Django 单仓库中的业务逻辑回归、API 契约变化和配置错误。系统只声明同一仓库内未见故障的泛化能力。

2. **总体架构**：系统划分为 Task Intake、Diagnosis、Retrieval、Tool Runtime、Sandbox、Reporting 和 Evaluation 七个边界。边界之间只交换显式 DTO 与 artifact 引用，不传递 FastAPI 请求对象或基础设施实现对象。

3. **主应用接口**：诊断应用服务是 CLI、FastAPI 和离线评测器共享的最高层入口。它接收 Diagnosis Task，创建 Diagnosis Run，并提供状态、事件、最终 Root Cause Report 与 artifact 引用。CLI 和 FastAPI 不复制诊断逻辑。

4. **任务输入契约**：Diagnosis Task 必须包含本地仓库或冻结 benchmark 标识、base commit、Faulty Commit、CI 日志 artifact、注册测试命令 ID、容器镜像摘要、允许修改的源码范围，以及时间、Token 和工具调用预算。系统自行生成故障 diff。

5. **任务有效性**：任何必填字段非法、commit 不存在、镜像不匹配或目标失败无法复现的任务都成为 Invalid Task，不进入诊断状态机，也不计为诊断错误。

6. **诊断聚合**：Diagnosis Task 是事务边界，管理一个 Diagnosis Run、最多三个活跃 Hypothesis、Evidence、Experiment、预算、停止原因和报告引用。

7. **状态机**：采用自研、类型化、可回放状态机。主要阶段为任务校验、工作区准备、形成 Hypothesis、选择 Experiment、执行工具、更新 Evidence、验证补丁和生成报告。

8. **假设生命周期**：Hypothesis 状态限定为 proposed、testing、supported、rejected 和 inconclusive。实验失败只有在其预期 Observation 足以证伪假设时，才允许进入 rejected。

9. **候选数量**：同时活跃的 Root Cause Candidate 不超过三个。新 Evidence 可以调整排序；被拒绝候选必须获得新 Evidence 后才能重新进入竞争。

10. **证据排序**：Evidence Score 使用预先定义的简单整数规则。强度顺序为可复现实验、直接堆栈或代码、Git 关联、语义相似性。该分数只用于排序，不表示概率，只允许在验证集做一次有限校准。

11. **工具调用约束**：每次工具调用必须关联 Hypothesis、调用原因、预期 Observation 和权限类别。没有活跃 Hypothesis 的探索性调用必须被状态机拒绝。

12. **停止策略**：候选补丁通过 Public Validation、达到 15 次工具调用、达到时间/Token/成本预算、连续三步无关键 Evidence 变化，或所有候选耗尽时停止。证据不足是合法结果。

13. **上下文策略**：模型常驻上下文只包含任务目标、最多三个活跃 Hypothesis、Evidence 表、Experiment 摘要、预算、最近动作和必要原文。完整日志、代码、测试输出和模型原始响应保存在上下文之外。

14. **结构化模型输出**：模型输出必须通过 Schema 校验。失败时保存原始响应和错误，允许一次明确纠错；再次失败记为 Schema Failure，不使用模糊解析静默修复。

15. **ModelProvider**：模型通过独立 HTTP 推理服务和最小适配接口调用，Agent 进程不直接加载模型。开发阶段本地优先；本地质量门槛失败时，最终评测允许云端兜底。

16. **工具运行时**：Tool Spec 定义名称、版本、输入输出 Schema、权限、超时、结果上限、错误语义和副作用。错误至少分为参数错误、权限拒绝、超时和执行失败。第一版不实现 MCP，也不默认自动重试工具。

17. **冻结工具集**：Agent 仅可使用统一代码搜索、按行读取代码、检查符号关系、检查故障 diff、运行注册测试、在实验工作区应用补丁和执行静态检查七类工具。不得提供任意 Shell、网络查询或生产系统工具。

18. **代码分析**：代码块以 Python AST 的函数、方法和类为主要单元，超长单元再按 Token 窗口拆分。符号分析只提供定义、引用、导入和近似调用边，不宣称得到完整 Python 调用图。

19. **检索查询**：确定性查询信号来自异常类型、消息、堆栈、失败测试和文件符号；动态语义查询由 Agent 根据当前 Hypothesis 生成。每条动态查询都必须能追溯到对应 Hypothesis。

20. **检索接口**：Agent 只看到统一的代码搜索接口。BM25、向量、混合及混合加 reranker 是评测时冻结的后端配置，不由 Agent 选择。

21. **索引安全**：只索引 Faulty Commit 快照。修复后代码、修复 diff、答案性 commit message 和未来 commit 不得进入索引或 Agent 上下文。

22. **沙箱边界**：每个 benchmark 仓库使用预构建、依赖锁定的镜像。运行采用非 root 用户、关闭网络、只读基础镜像、临时工作区和 CPU/内存/时间限制，不挂载宿主凭证。

23. **沙箱声明**：沙箱只防止正常测试的意外破坏，并隔离不受信任但非刻意恶意的开源代码；不声明抵御容器逃逸、恶意代码或生产多租户攻击。

24. **实验权限**：Agent 可以运行注册测试、添加临时插桩、创建探索性测试和临时修改业务代码。它不能修改、删除或跳过已有测试，不能访问 Hidden Validation，也不能修改依赖锁、评测器或容器配置。

25. **补丁流程**：实验改动与最终候选补丁分别记录。Root Cause Candidate 按排序逐个验证；候选通过 Public Validation 后提升为 Top-1，并停止生成其他正式补丁。

26. **Hidden Validation 隔离**：补丁封存后，由独立评测器运行原失败测试、邻近行为测试、防投机测试和静态补丁约束。结果只用于评分，不反馈给 Agent。

27. **持久化**：SQLite 保存任务、运行、结构化状态和追加事件。日志、代码、补丁、测试输出和模型响应作为内容寻址 artifact 存储，数据库只保存其引用与完整性元数据。

28. **运行事件**：事件至少覆盖 Hypothesis 创建、Evidence 添加、Experiment 启动、工具完成、Hypothesis 拒绝、补丁验证和运行停止。事件记录结构化决策摘要，不依赖私有思维链。

29. **服务模式**：MVP 是仅绑定本机的单用户服务，不接受任意代码上传。单个后台 worker 串行执行任务；服务重启时未完成任务标记为 interrupted，不自动恢复。

30. **用户入口**：CLI 是主要实时演示入口；FastAPI 只提供任务提交、状态查询和报告读取。静态 HTML/JSON 报告用于展示完整轨迹、消融、Baseline 和失败案例。

31. **数据集**：冻结 30 个 Diagnosis Task，按 12 个开发、6 个验证、12 个隐藏划分；原则上三类支持故障各 10 个，目标组成是 24 个可控注入和 6 个真实修复任务。

32. **数据难度**：至少一半任务包含多个合理候选改动，并要求结合日志、依赖关系或 Experiment 判断 Root Cause。不得用明显无关噪声机械增加难度。

33. **标准答案**：每个任务标注触发条件、Root Symbol、故障机制、传播路径、失败表现、正确修复行为、参考补丁和 Hidden Validation。

34. **检索评测**：使用冻结标准查询分别评测四种检索配置，报告 Recall@K、MRR、Root Symbol 命中和辅助证据覆盖。检索评测不运行完整 Agent。

35. **端到端方案**：验证集选定一个检索配置后，在隐藏集比较 Raw Model Baseline、Fixed Pipeline 和动态 Agent。三者共享诊断模型、故障输入、检索配置和验证环境。

36. **Fixed Pipeline**：固定流水线按预先冻结的顺序解析日志、读取 diff、检索一次、读取固定数量代码、运行一次失败测试、单次生成报告和补丁并执行相同 Validation。它不能根据中间结果追加查询或改道。

37. **因果评分**：Root Symbol 位置使用确定性匹配。触发条件、机制、传播、失败表现和修复行为由不同模型家族的匿名 Judge 按 0、1、2 逐字段评分，并由作者复核全部隐藏任务。

38. **复现性**：每次评测生成不可变 Run Manifest，记录模型与量化版本、推理参数、随机种子、prompt、索引、仓库、镜像、预算、任务顺序和已知非确定性。

39. **失败分类**：至少区分 Invalid Task、Infrastructure Failure、模型失败、Agent 决策失败、诊断错误和成功。所有类别报告原始数量与统一分母，不静默剔除失败。

40. **API 成本与模型用量**：记录每次 Diagnosis Run 的输入、缓存输入、输出 Token、模型调用、工具调用和耗时。动态 Agent 的中位 Token 成本不得超过 Fixed Pipeline 的三倍。

41. **本地模型门槛**：本地模型进入完整评测前，必须适配 8 GB 显存、结构与工具参数成功率达到 90%、三个代表任务至少两个命中 Top-3、能生成可应用补丁且重复运行不产生完全不同的无证据结论。

42. **延迟边界**：本地开发任务最多运行 15 分钟；实时演示选择五分钟内可完成的冻结任务；复杂案例使用明确标记的真实运行回放。

43. **交付降级**：若进度落后，依次移除 FastAPI、界面美化、部分真实 commit；不得削减状态机、工具运行时、RAG 消融、沙箱、评测隔离或标注质量。

## Testing Decisions

1. **测试哲学**：测试只观察外部行为和领域不变量，不断言内部函数调用顺序、私有字段或 prompt 的逐字内容。重构内部模块时，只要契约和行为不变，测试不应失败。

2. **最高测试缝**：主验收缝是诊断应用服务。测试输入完整 Diagnosis Task，通过替身 ModelProvider、检索器、工具和沙箱驱动一次 Diagnosis Run，最终断言 Root Cause Report、事件、artifact、停止原因和失败分类。CLI、FastAPI 和评测器都复用此缝，不各建一套端到端测试。

3. **纵向闭环测试**：至少一个冻结任务必须覆盖从任务校验、Hypothesis、工具调用、检索、候选补丁、Public Validation、报告到事件回放的完整链路。该测试允许使用确定性 FakeModelProvider，但不能绕过真实状态机和工具运行时。

4. **任务契约测试**：验证缺失 commit、不可用镜像、未知测试命令、越界可写路径和不可复现故障均产生 Invalid Task，且不会启动模型或沙箱。

5. **领域状态测试**：通过公开状态机接口验证最多三个活跃 Hypothesis、合法状态转移、反证语义、预算耗尽、连续无新 Evidence 停止和证据不足结果。

6. **Evidence Score 测试**：验证实验、直接代码、Git 关联和语义相似性的单调强度顺序，验证 Contradicting Evidence 会降低排序，并验证分数不会被输出为概率。

7. **模型契约测试**：使用 FakeModelProvider 验证合法结构输出、首次 Schema Failure 后纠错成功、二次失败终止，以及原始响应和校验错误被保存。

8. **工具契约测试**：对所有 Tool Spec 执行相同契约套件，验证输入输出 Schema、权限、超时、结果截断、artifact 引用、错误分类和副作用声明。

9. **工具安全测试**：验证路径穿越、仓库外读取、非白名单命令、测试文件修改、隐藏测试访问和禁止目录补丁均被拒绝并留下审计事件。

10. **检索单元测试**：验证 AST 语义块保留文件、Root Symbol、父类和行区间；超长块分窗后仍保留符号归属；动态 Python 关系明确返回未知而不是伪造精确边。

11. **检索消融测试**：对同一冻结查询和同一故障索引运行四种 Retrieval Configuration，验证输出可计算 Recall@K 与 MRR，且所有方案只访问 Faulty Commit。

12. **上下文测试**：验证大日志、代码和测试输出被移至 artifact，模型上下文保留引用；验证上下文预算不会因完整历史追加而无限增长。

13. **沙箱集成测试**：在真实容器运行最小仓库，验证非 root、禁网、资源限制、超时、临时工作区、基础镜像只读以及没有宿主凭证挂载。

14. **实验隔离测试**：验证临时插桩和探索性测试不会进入最终候选补丁，且一次失败 Experiment 不会在缺少证伪条件时错误拒绝 Hypothesis。

15. **补丁防投机测试**：验证修改/删除/跳过测试、宽泛异常静默、删除公共 API、硬编码失败输入和修改评测基础设施会被静态规则或 Hidden Validation 拒绝。

16. **Hidden Validation 隔离测试**：验证评测器只在补丁封存后运行隐藏测试，隐藏输出不会出现在 Agent 上下文、事件或后续模型请求中。

17. **持久化集成测试**：验证任务、运行和事件写入 SQLite，大对象写入 artifact store；验证哈希完整性、重复内容复用和引用不存在时的明确错误。

18. **重启行为测试**：模拟服务中断，验证未完成 Diagnosis Run 被标记为 interrupted，且不会被自动恢复或误报成功。

19. **接口一致性测试**：使用同一 Diagnosis Task 验证 CLI 与 FastAPI 返回相同任务 ID、状态语义和报告内容，不测试框架内部实现。

20. **事件回放测试**：验证追加事件能够重建用户可见的 Hypothesis、Evidence、Experiment 和最终状态；回放必须明确标记，不能伪装为实时运行。

21. **Baseline 公平性测试**：验证 Raw Model Baseline、Fixed Pipeline 和动态 Agent 使用相同模型、任务输入、检索版本与镜像；验证 Fixed Pipeline 不能动态追加工具。

22. **评分器测试**：使用人工编写的完全正确、部分正确和错误样例验证字段级 0、1、2 rubric；验证 Judge 输入已匿名且不会看到系统名称。

23. **失败分类测试**：分别注入任务、模型、容器、工具和 Agent 决策失败，验证报告中的分类、分母和重试行为正确。

24. **确定性与复现测试**：验证 Run Manifest 包含全部冻结版本和参数；对相同 manifest 重放时，环境和工具输入必须一致，无法消除的模型非确定性必须被记录。

25. **真实模型测试**：默认 CI 不调用真实模型。少量显式标记的 live-model 测试验证本地服务兼容性和结构输出门槛；录制响应不得包含隐藏任务答案。

26. **端到端评测验收**：隐藏集 Top-1 不低于 50%，Top-3 不低于 75%，结构化因果字段平均正确率不低于 70%，Top-1 至少比最佳 Baseline 多命中两个任务，补丁 Hidden Validation 通过率不低于 50%。

27. **稳定性验收**：最终 Agent 在 12 个隐藏任务上重复运行三次，至少 10 个任务保持相同规范化 Top-1 Root Symbol。

28. **成本验收**：报告每个方案的质量、Token、模型调用、工具调用和耗时；动态 Agent 的中位 Token 成本不得超过 Fixed Pipeline 的三倍。

29. **人工复核**：人工复核全部 12 个隐藏任务的因果评分，记录同意、修正和无法判断，并报告与 Judge 的一致率。

30. **测试先例**：仓库尚无实现和测试文件，因此不存在可复用测试先例。本 specification 建立诊断应用服务这一主缝；后续模块测试不得绕开该缝重复搭建平行端到端体系。

## Out of Scope

- 生产告警、Trace、Metrics、日志平台或线上环境接入；
- 外部服务故障、容量与性能问题、随机失败、flaky 测试和并发故障；
- 非 Python 语言以及跨语言符号分析；
- 对不同仓库、不同框架或未知项目的泛化保证；
- 完整、精确的 Python 静态调用图；
- 运行时多 Agent 协作；
- MCP Server/Client 支持；
- 任意 Shell、任意网络访问和任意用户上传代码；
- 自动修改真实仓库、推送分支或创建 PR；
- 公网部署、身份认证、多用户、租户隔离和分布式任务队列；
- 生产级容器安全、恶意代码防御和容器逃逸防护；
- 服务重启后的自动任务恢复；
- 自动识别所有语义性“作弊补丁”；
- 用补丁通过率替代 Root Cause 位置和因果解释评分；
- 第一版自主选择 BM25、向量检索或 reranker；
- 第一版训练检索、排序、Evidence Score 或概率校准模型；
- 复杂 Web UI、移动端或远程协作功能。
